# Pilot full-text recovery

Step 5b recovers all available text from the mapped introduction (148) and body
(149) of `8802065`. Text stays private regardless of publication or future access
policy. It is not yet verified against the original viewer, and text inside
image resources is not transcribed by this step.

The plain-text files are convenience exports, not a faithful reading edition.
The [subsequent structural review](CD1-BLOCK-STRUCTURE-8802065.md) adds required
block identification and a derived Markdown preview before image mapping. Keep
the RTF and structured paragraph/run recovery as preservation sources.

## Reproduce and read

From the repository root:

```sh
python3 -m tools.recover_cd1_text
```

The command validates the source, topic map, reviewed RTF inventory, and earlier
paragraph record. It compares its result with the
[tracked recovery metadata](../data/catalog/text-recoveries/cd1-8802065.json)
before writing these files under ignored `build/cd1-text/8802065/`:

| File | Contents |
| --- | --- |
| `introduction.txt` | UTF-8 introduction, separate from the body |
| `body.txt` | UTF-8 body with ordered object placeholders |
| `article.json` | Paragraphs/runs, observed formatting, source spans, separate metadata, and a byte-accounting ledger |
| `provenance.json` | Input/output checksums, counts, decisions, and verification status |

`--write-record` deliberately regenerates the committed metadata. It does not
publish the text. Outputs are replaced individually after validation; rerun after
an interrupted write before using them as a set. Repeated runs are deterministic.

## Result and interpretation

- **4 introduction paragraphs**, including two blank paragraphs: 192 characters
  including line endings.
- **319 body paragraphs**, including 81 blank paragraphs: 27,686 characters
  including line endings and placeholders. These are RTF paragraphs, including
  individual example/code lines, rather than a count of editorial prose blocks.
- **268 decoded text runs**, with no undecoded runs or replacement characters.
  CP949 decoding is strict and each run re-encodes to its original text bytes.
- **21 object placeholders**, each preserving its resource name, command type,
  paragraph/run position, and original byte span. `[object:...]` strings in the
  text files are generated markers; typed object runs distinguish them from
  source text in the JSON.
- **All 149,579 source bytes / 40,351 tokens accounted for**, as text bytes,
  formatting, paragraph boundaries, metadata, object references, decompiler
  guards, or physical RTF layout.

The first prose paragraph exactly reproduces step 4's 182-character sample and
UTF-8 output hash. Native context footnotes, keywords, browse-sequence markers,
and the hidden navigation link remain in a separate metadata array as raw RTF
with source positions. They do not appear in the visible prose. Visible title,
page label, and byline remain where they occur in the body; this step makes no
new catalog matching or author-identity decisions.

## Formatting and source fidelity

Each paragraph retains observed RTF paragraph properties (`li`, `ri`, `sl`,
`sa`, `sb`, `keepn`, `qr`), and each run retains font ID, explicit half-point size,
bold, and underline. `pard` clears paragraph properties; `plain` resets character
properties to the document's default font. A null size means there is no explicit
size since that reset, rather than an invented rendering size. Metadata groups
cannot leak their font/format changes into visible text. The body inherits the
introduction's ending state across the topic delimiter.

Original spaces, spelling, punctuation, blank paragraphs, and example/code line
order are preserved. No Unicode normalization, whitespace collapsing, automatic
heading inference, table reconstruction, or syntax highlighting is applied.
Physical RTF CR/LF bytes are layout; each `par` becomes one output LF. The five
documented HELPDECO literal-brace guards are omitted through recorded
transformations, preserving literal example braces without spurious hyphens.

Each text run has source spans and a hash of the unescaped encoded bytes. A run
that cannot decode would retain its original bytes, source spans, issue reason,
and an explicit placeholder; later runs could still be recovered. Unknown visible
controls are rejected rather than silently dropped. The current pilot has no
such failures. This remains a bounded reader for the reviewed subset, not a
general-purpose RTF converter.
