# CD1 pilot raw topic map

Step 3 maps reference `8802065` to the native context table and raw RTF topic
boundaries. The [metadata-only map](../data/catalog/topic-maps/cd1-8802065.json)
extends the [step 2 metadata match](CD1-MATCH-8802065.md); it does not change that
earlier decision or claim decoded/verified article content.

## Reproduce

From the repository root, with the original private sources available:

```sh
python3 tools/map_cd1_topic.py
```

The default command reads the sources and checks the committed map without writing
files. `--write` regenerates that metadata record deterministically. No HELPDECO
executable or temporary checkout is needed. The two full input SHA-256 hashes
must match the preserved MVB/RTF snapshots; another extraction needs an explicit
review rather than silently reusing these offsets. Run `make check` for the
focused native-address tests and existing importer tests.

## Evidence chain

1. The index target `8802065` hashes to **`0x0e688271`** using the native
   WinHelp context algorithm. HELPDECO's generated alias **`2PES_R6`** has exactly
   the same hash. This alias is not a recovered original context name.
2. The native `|CONTEXT` leaf entry at MVB byte **232793464** contains that
   hash and logical `TOPICOFFSET` **1575226 (`0x0018093a`)**.
3. Walking native `|TOPIC` links reaches topic number 148 (one-based ordinal 149)
   at that offset. Its header starts at MVB byte **201987493**, with logical
   `TOPICPOS` **789925**. Its native title is “유닉스란 무엇인가?”.
4. The corresponding RTF topic contains the `2PES_R6` context footnote. Its
   hidden link `{\v 3M4UMD}` at RTF byte **378402** resolves through the native
   context table to the preceding topic, ordinal 148. That short topic has the
   same visible heading and introductory content; it is retained separately.
5. Native next-topic pointers and RTF topic delimiters agree on the following
   untitled separator and neighboring article. The body's browse-forward offset
   points to ordinal 152, whose native title is “스펠링 체커”. This browse link
   therefore does not establish continuation of the UNIX feature.

This establishes the reference-to-topic relationship using native context and
link evidence, independently of title similarity. The intro/body roles are a
structural interpretation still awaiting the original viewer comparison.

## Raw boundaries

All RTF byte ranges below are zero-based, end-exclusive, and refer to the exact
74,157,536-byte `private/cd1-probe/raw/MASOCD.rtf` snapshot. They exclude the
six-byte `\page` plus newline delimiter on either side. They include raw topic
footnotes/formatting and are **not standalone RTF documents**; later decoding
also needs the source document's font/header information.

| Ordinal | Role | Context alias | RTF byte range | Length |
| --- | --- | --- | --- | --- |
| 148 | Linked introduction | `3M4UMD` | `[376628, 377938)` | 1,310 |
| 149 | Reference target/body | `2PES_R6` | `[377944, 526213)` | 148,269 |
| 150 | Untitled separator, excluded | none | `[526219, 526228)` | 9 |
| 151 | Next article introduction, excluded | `3M4LHC` | `[526234, 527545)` | 1,311 |
| 152 | Next article body, excluded | `1KN6EK` | `[527551, 553864)` | 26,313 |

The separator contains only `\pard \b ` in the RTF. Omitting it from the map
would hide a real native topic and make topic numbering misleading. The JSON
also records slice hashes, native header positions, context-entry byte positions,
and browse offsets. Native `TOPICOFFSET` and `TOPICPOS` are logical addresses;
neither is an offset into the MVB or RTF file.

The body has the explicit ASCII label **`88.2.  65p`** at RTF bytes
`[378317, 378327)`. This supports the TOC's page 65 for this pilot, beyond the
conditional reference-suffix comparison in step 2. It does not verify printed
pagination, the ending page, or a general rule for other native references.

## Implementation limits and next check

The tool deliberately supports only these pinned sources. Internal-file
locations come from the preserved CD1 directory listing. It reads all 2,103
context leaf records, walks native topic links only through ordinal 152, and
checks selected native/RTF ordinals against their context hashes. It does not
implement a general RTF parser or a general compressed MVB reader.

The format interpretation follows the pinned HELPDECO revision
[`b9c187a20d83a3e738d8fe073eb924a8b7264c5c`](https://github.com/joncampbell123/helpdeco/tree/b9c187a20d83a3e738d8fe073eb924a8b7264c5c),
specifically `helpfile.txt` (`|CONTEXT`, `|TOPIC`, and address structures),
`helpdeco.c` (`hash`, `SysLoad`, `TopicRead`, `NextTopicOffset`, `TopicDump`), and
`helpdec1.c` (`scanlong`, `scanword`). Inspection found a detail requiring the
implementation rather than the general format prose: this uncompressed MVB uses
4,096-byte physical blocks but a 16,384-wide logical TOPICPOS stride. The focused
cross-block test checks both the skipped block header and logical address gap.

The recovery scope is provisionally **introduction plus body (148–149)**. There
is no additional hidden link target in the body besides the introduction.
Completeness remains unverified: this bounded inspection cannot rule out material
reachable through other viewer navigation/macros or omitted by the decompiler.
Body text, tables, images, and any viewer-dependent behavior await later steps.

Next: decode **one paragraph** inside ordinal 149 with font/encoding provenance
and strict error handling. Keep the introduction separate and exclude ordinals
150–152. Original viewer evidence remains a step 7 requirement.
